START HERE 01

An agent is a loop with boundaries.

A chat model returns text. An agentic app gives a model a job, useful context, and a small set of tools. It checks what the model wants to do, runs an allowed action, reads the result, and either continues or hands control back to a person.

“

The model proposes. The application decides what is allowed to happen.

A useful rule for every agent feature

AGENTIC APP CONCEPTS 04

Find each idea in the code.

These are product engineering concepts. A model call matters, but so do state, permissions, delivery, and proof that the whole path works.

Built in repo Limited or gated

01BUILT

Orchestration

Turn a user goal into a controlled cycle of context, model decisions, tools, and results. Keep app state and policy outside the prompt.

Agent orchestration Persistent workflow
02BUILT

Tools and MCP

Give the model narrow capabilities, validate each request, and audit the execution. Do not turn tool use into arbitrary computer access.

Tool execution MCP policy
03BUILT

Knowledge and RAG

Retrieve relevant approved information at answer time. Retrieval improves grounding; it does not prove that a generated answer is true.

RAG service Knowledge browser
04BUILT

Memory and state

Keep chat history, decisions, queues, delivery status, and recovery data durable. Operational memory is more than adding old messages to a prompt.

Memory service agentd persistence
05BUILT

Policy, approvals, and autonomy

Separate what the model recommends from what the product permits. Observe mode records events, draft mode asks for review, and auto-reply mode still checks consent, sensitivity, configuration, channel rules, and delivery state. Owners can pause or escalate.

Autonomy policy Decision evidence Supervisor
06BUILT

Channel adapters

Normalize incoming events while keeping each provider's consent, authentication, rate, and delivery rules at its boundary.

agentd channel workers Channel inventory
07GATED / LIMITED

Evaluation, observability, and recovery

Record decisions and delivery outcomes, evaluate autonomy quality, and test restarts, retries, and migrations. A unit test cannot prove a live provider account, signed release, or customer deployment works.

Testing guide Release gates Behavior contract
A REPEATABLE BUILD METHOD 05

Build an agent in this order.

The repo's history suggests a practical sequence for a small team. It keeps each new source of uncertainty visible.

  1. 01
    Pick one job.

    Write the user, trigger, allowed outcome, and handoff condition.

  2. 02
    Make a vertical slice.

    Connect one channel to one model response and one user-visible result.

  3. 03
    Add context and tools.

    Retrieve approved facts. Expose only actions that the workflow needs.

  4. 04
    Put policy around action.

    Check identity, consent, sensitivity, budget, and human-review rules.

  5. 05
    Persist state and evidence.

    Save decisions, retries, delivery acknowledgements, and recovery status.

  6. 06
    Prove the edges.

    Evaluate quality. Test duplicate events, restart, pause, failures, and upgrades.

READ THE EVIDENCE CAREFULLY 06

Useful lessons.
Honest limits.

This repository is a single-owner, local-first product. It is not proof that a hosted, multi-tenant agent is ready for production.

  • 01Some channel automation remains experimental, disabled, or dependent on live-provider checks.
  • 02RAG gives the model material to use; it cannot guarantee a correct answer.
  • 03Passing unit tests does not prove OAuth, webhook delivery, signed packages, or real hardware behavior.
  • 04The repo shows a bounded product agent, not a swarm of cooperating agents.

THE TAKEAWAY

Good agents are built
around what they may do.

Start with a clear job. Give the model context and narrow tools. Put application rules around every consequential action. Save evidence so people can review, recover, and improve the system.
